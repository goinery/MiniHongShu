# HongShu 功能与技术价值说明（Java 简历项目）

> 整理日期：2026-10-30。依据当前仓库的 Controller、Service、Mapper、前端页面、依赖和部署脚本整理；“已实现”表示存在对应代码，不代表本次已完成运行验收或性能测试。

## 1. 项目定位与阅读方式

HongShu 是一个图文内容社区，包含用户前台、运营管理后台和 Java 后端。业务主线是“用户登录 → 发布图文 → 后台审核 → 内容发现 → 点赞、收藏、评论、关注 → 私信与通知”，同时提供会员、分类、标签、专辑、反馈等运营能力。

作为 Java 简历项目，优先展示事务、并发控制、身份认证、查询优化和资源生命周期管理，再用后台管理功能证明业务完整度。管理端沿用了 RuoYi 风格的系统管理与权限基础，面试时应区分基础框架能力和本人实际承担的业务开发、改造工作。

本文采用以下价值分层，功能清单在各业务域内按价值优先介绍：

| 层级        | 简历价值判断                                                     | 使用方式                         |
|-------------|------------------------------------------------------------------|----------------------------------|
| A：核心亮点 | 有明确的一致性、并发、权限或资源管理问题，可以深入解释实现与取舍 | 优先写进项目职责，准备代码级追问 |
| B：业务支撑 | 涉及多表关系、分页、聚合、批量查询或完整业务流转                 | 支撑项目介绍，选择熟悉的部分展开 |
| C：基础配套 | 常规增删改查、页面交互和通用运维能力                             | 证明完整度，适当合并描述         |
| 边界 / 预留 | 只有配置、接口、基础组件，或尚未形成完整链路                     | 单独说明，不作为已交付亮点       |

## 3. 核心功能与对应技术

### 3.1 用户认证与会话（A）

| 功能                             | 实际实现与对应技术                                                                                                                           | Java 简历价值                                  |
|----------------------------------|----------------------------------------------------------------------------------------------------------------------------------------------|------------------------------------------------|
| 手机号密码登录、首次登录自动注册 | 校验手机号与密码；首次创建会员、会员号及默认资料；密码经 BCrypt 编码；Spring 事务编排                                                        | 账号生命周期、业务校验、密码存储               |
| 历史密码迁移                     | 兼容历史 MD5；用户验证成功后将密码升级为 BCrypt                                                                                              | 不重置用户密码的存量数据迁移                   |
| Access Token 与 Refresh Token    | JWT 携带用户 ID、会话 ID、令牌类型；Redis 保存当前会话 ID；刷新时校验 refresh 类型并限制新 access 的有效期                                   | 双令牌职责、令牌过期与服务端状态结合           |
| 登录态撤销与替换                 | 退出登录删除 Redis 会话；新登录覆盖同一用户的会话 ID；旧令牌与当前会话不匹配即失效                                                           | JWT 到期前失效、单用户当前会话控制             |
| 账号停用、改密后的会话处理       | 请求时复核会员状态；后台停用、修改会员密码或删除会员时撤销其会话                                                                             | 管理动作与线上身份状态联动                     |
| 身份上下文和公开接口             | MVC `HandlerInterceptor` 校验 `accessToken`；`AuthContextHolder` 维护请求内用户 ID；`afterCompletion` 清理；`@NoLoginIntercept` 支持游客访问 | 避免信任客户端提交的用户身份、避免线程复用残留 |
| 会话失效后关闭实时连接           | 发布 Spring 会话失效事件，由 WebSocket 注册器关闭该用户连接                                                                                  | 事件解耦、HTTP 与长连接的认证一致性            |
| 浏览器恢复与自动刷新             | 路由进入时向服务端校验身份；Axios 用共享 Promise 合并同一会话的刷新请求，原请求最多重试一次                                                  | 减少重复刷新，保持前后端登录状态一致           |
| 切换账号时隔离迟到响应           | 前端记录会话版本；丢弃旧账号请求、刷新结果和 WebSocket 初始化结果                                                                            | 异步竞态处理，防止旧请求以新账号身份重发       |
| 登录、退出记录                   | 异步写会员登录日志，记录时间、IP、浏览器等信息                                                                                               | 请求与日志任务解耦                             |

代码入口：[前台认证服务][web-auth]、[会话服务][web-session]、[认证拦截器][web-interceptor]、[会员管理服务][sys-member]、[前端会话状态][user-store]、[Axios 请求层][web-request]。

### 3.2 私信、会话与社交通知（A）

| 功能                       | 实际实现与对应技术                                                                             | Java 简历价值                               |
|----------------------------|------------------------------------------------------------------------------------------------|---------------------------------------------|
| 一对一文字、图片私信       | 通过 HTTP 发送；后端覆盖发送人身份，校验接收者、消息类型和内容；图片校验文件可用性             | 消息输入校验、服务端身份可信边界            |
| 私信持久化与双向会话摘要   | MySQL 保存消息，为双方维护会话预览、时间和未读数；在同一事务内更新                             | 多表事务、会话模型设计                      |

| 离线历史、分页加载         | 消息始终入库；登录后查询会话与历史；分页限制及偏移溢出校验                                     | 实时推送与持久化职责划分                    |

| 私信未读清零               | MySQL 会话表更新；与发送操作采用相同的参与者行锁边界                                           | 未读数与读写事务协调                        |
| WebSocket 鉴权             | `/web/ws/{uid}` 校验令牌身份与路径用户一致；投递前再次校验有效会话                             | 避免冒充用户订阅或接收消息                  |
| 连接替换、断线清理         | `ConcurrentHashMap` 保存本实例连接；同用户新连接替换旧连接；按连接对象条件移除；单连接同步发送 | 并发容器、旧关闭回调竞态、连接级互斥        |
| 点赞收藏、评论、关注通知   | 各业务在事务提交后增加通知计数并推送；跳过部分自通知；异常记录日志                             | 将业务提交与通知投递时机协调起来            |
| 社交未读数查询、增加、清零 | Redis 中按用户保存三类 JSON 计数；Lua 完成读取、修改、写回                                     | 避免普通 GET / SET 并发覆盖和跨类别计数丢失 |
| 消息中心与断线重连         | 三类社交通知列表、私信列表、角标；前端按消息类型分发，支持有上限的递增延时重连                 | 实时事件与页面状态同步                      |

代码入口：[聊天应用服务][web-chat]、[聊天数据访问][chat-repository]、[提交后消息投递][chat-publisher]、[社交通知入口][chat-utils]、[通知 Lua 计数][chat-notifications]、[连接注册器][ws-registry]、[前端消息连接][messaging]。

能力边界：连接表属于单个 JVM；没有跨实例消息路由、消息确认、失败重试队列或恰好一次投递。历史查询能读取已保存私信，但不能据此宣称具备完整的可靠消息中间件能力。

## 7. 建议重点讲解的技术设计

### 7.1 “数据库已提交”与“用户看到消息”的先后关系

私信和社交通知都将推送放到业务事务提交后：私信先写消息和双方会话，再在 `afterCommit` 推送；点赞、评论、关注先写关系或内容，提交后再更新通知计数并投递。

可以讲清楚两个结果：数据库回滚时不发成功通知；推送失败不会把已提交业务显示为失败。同时要交代限制：进程在提交后、回调前退出仍可能漏通知，当前没有 Outbox 或持久化补偿机制。

### 7.2 为什么关注与私信要固定加锁顺序

双方用户记录始终比新建会话或关注关系更早存在，适合作为首次操作的互斥点。代码先解析数据库实际 ID，再按固定顺序逐行加锁，随后用当前读判断关系状态；这样能协调同一用户对的并发操作，减少双方互相加锁造成的死锁风险。

需能解释隔离级别、普通快照读和 `SELECT ... FOR UPDATE` 的区别。用户行锁会让共享同一用户的部分写操作串行，这也是当前方案的吞吐取舍。

### 7.3 Redis Lua 解决的是哪一类计数问题

社交通知的三类计数保存在同一个 JSON 对象中。若业务分别 GET、修改、SET，会覆盖其他并发请求的结果。Lua 在 Redis 内一次完成解析、指定字段增减 / 清零和保存，避免这种覆盖。

这项设计对应社交通知计数；私信未读数仍在 MySQL 会话表里，笔记的点赞 / 收藏数也主要由 MySQL SQL 更新，不能将它们笼统说成“所有计数都在 Redis”。

### 7.4 如何让文件跟随业务记录正确回收

新文件上传后登记归属；登记或事务失败时补偿删除。编辑、删除业务记录时先保留旧引用，事务提交后再查是否还有笔记、头像、专辑等引用，确认不用才删除。清理使用独立事务，避免继续依赖已经完成的业务事务。

适合追问的点包括：共享封面不能直接删；数据库事务不能回滚 OSS；外部图片不是受管资源；回收失败目前只记录日志，下一步可引入持久化清理任务。

### 7.5 如何减少关联列表的查询次数

笔记、动态、评论和会话列表会先收集本页用户 / 内容 ID，再用批量查询与 Map 装配。评论回复预览在数据库用窗口函数限制每组最多 3 条；点赞收藏通知还将互相独立的查询放进受管线程池并行执行。

可说明这是对逐条查询和过量加载的改进；没有基准测试时，不写“响应速度提升 X%”。`CompletableFuture` 的异步查询也不自动共享请求线程的事务或 ThreadLocal 身份。

### 7.6 如何让删除操作维护关联与统计

笔记删除集中到共用服务，按顺序锁定并检查权限，清理关联表，刷新作者和专辑派生数据，再安排提交后的文件回收。评论删除同样复用服务，先锁笔记再锁评论，删除下级回复及点赞后调整计数。

这体现的是业务聚合的应用层编排和本地事务，而不是依赖数据库外键自动完成全部级联。

### 7.7 如何让 JWT 支持主动下线

前台 JWT 除用户 ID 外还绑定会话 ID 和令牌类型，服务端用 Redis 当前会话做校验。退出或账号状态改变时撤销会话；新登录替换会话，使旧 Token 失效；Spring 事件通知本实例断开旧 WebSocket。

需区分前台双令牌方案和后台 Spring Security 登录对象方案。前台刷新当前保持 refresh Token，不应描述成已实现 Refresh Token 每次轮换与重放检测。

### 7.8 统计缓存为什么要考虑跨日

周访问统计缓存 Key 包含日期，TTL 取十分钟与到下个零点剩余时间的较小值，跨日完成的旧请求不再写入缓存。日期标签、查询边界和缓存日期使用同一时间基准，减少午夜跨日数据错位。

这是已有统计查询的缓存处理细节，不能替代尚未完善的访问数据采集链路。

### 10.1 项目介绍示例

> HongShu 图文社区：基于 Java 21、Spring Boot、MySQL、Redis 和 Vue 3 的前后端分离社区系统，覆盖图文发布审核、内容检索、评论回复、关注收藏、私信通知及运营管理。后端采用 Maven 多模块单体结构，管理端基于 RuoYi 风格的权限体系扩展社区业务。

### 10.2 项目职责示例

以下条目按当前代码能力编写，选择本人实际完成并能解释的 3–5 条使用；框架已有功能不能直接写成本人从零实现。

1. **私信与通知**：实现文字 / 图片私信、双向会话摘要和未读管理，通过 MySQL 事务及固定顺序行锁协调会话写入，在事务提交后推送 WebSocket 消息，并使用 Redis Lua 原子维护社交通知计数。
2. **会话认证**：基于 JWT 双令牌和 Redis 会话 ID 实现前台登录态校验、刷新、退出及账号停用后的会话撤销，通过会话失效事件联动关闭 WebSocket，兼容历史密码升级到 BCrypt。
3. **内容一致性**：编排笔记、标签、专辑与评论的写入和删除事务，统一资源归属与可见性校验，通过字段级 SQL 更新维护阅读、评论和互动统计。
4. **文件管理**：抽象 OSS 存储并登记文件归属，实现新上传文件失败补偿、旧文件提交后回收及业务引用检查，兼容历史本地资源，降低共享图片误删风险。
5. **查询优化**：按分页记录批量加载作者、目标内容和互动状态，使用 MySQL 窗口函数实现评论每组 Top N 回复预览，并用 CompletableFuture 并行装配互动通知列表。
6. **业务与交付**：完成审核、会员、分类、标签、专辑和反馈等运营流程，结合 RBAC、Excel、统计图表及 Docker Compose 编排形成可演示的社区项目。

### 10.3 建议演示顺序

1. 登录两个普通会员账号，展示个人主页、资料修改和浏览内容。
2. 发布图文，后台审核，观察内容进入首页 / 搜索；修改后展示重新待审。
